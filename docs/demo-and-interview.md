# 奇点排练 Agent：演示流程与面试讲解

这份文档用于两件事：第一次运行项目时按照固定路径看到完整效果，以及面试时用一条连贯故事解释为什么这些模块是 Agent，而不只是表单和 CRUD。

## 一、最短启动路径

排练模块的本地规则分支不依赖 LLM 或 Embedding API。没有模型 Key 时，仍然可以完成剧本解析、人工确认、规则检索式剧本问答、调度、排班、原词对词、舞台证据、资源检查、场记、复盘、排练度量、建议收件箱和知识资产演示。

在仓库根目录打开第一个终端：

```powershell
Copy-Item .env.example .env
python -m pip install -r requirements.txt
python -m uvicorn backend.main:app --reload --port 8000
```

再打开第二个终端：

```powershell
Set-Location frontend
npm install
npm run dev
```

访问 `http://localhost:5173`。默认登录信息来自 `.env` 的 `DEFAULT_EMAIL`、`DEFAULT_PASSWORD`；如果你已经修改过账号，以实际账号为准。首次模型配置引导不会阻止 `/rehearsal` 路由进入，但要使用适应性对词、LLM 复盘或 LLM 宣传文案时，仍需在设置页填写对应服务。

## 二、8 分钟完整演示

建议使用仓库内的示例剧本 [`docs/examples/qidian-demo-script.md`](examples/qidian-demo-script.md) 或 [`docs/examples/qidian-echo-room-script.md`](examples/qidian-echo-room-script.md)，以及演员档期 [`docs/examples/qidian-actor-availability.csv`](examples/qidian-actor-availability.csv)。

### 1. 剧本解析与人工确认

进入“排练工作台”，输入或上传示例剧本，使用 `rules` 或 `auto` 运行解析。

重点展示：

- 左侧原文仍然保留；
- 右侧展示场次、角色、台词、道具和 Agent trace；
- 每句台词有 `source_line`，可以回到剧本原文；
- 修改场次标题、角色或道具后再点击人工确认；
- 台词原文和来源行号不能被人工确认节点覆盖。

### 2. 剧本问答 RAG Agent

进入“剧本问答”，选择刚刚保存的剧本版本，提问“第一场小林拿起了什么？”：

- 查看回答中的证据编号、场次、来源类型和原文行号；
- 切换“规则检索”，说明没有 Embedding 也能完成可解释检索；
- 切换“语义检索”，如果没有 Embedding 配置，展示 `rules-fallback` 而不是报废；
- 将回答方式保持为“自动降级”，说明 LLM 只负责组织已检索事实，不能新增没有证据的剧情。

### 3. 演员排练表与调度 Agent

进入“演员排练表”，导入示例 CSV，先看预览和行级校验，再保存演员时间池。

回到排练工作台，选择已确认剧本并生成调度：

1. 先点击“预览调度”，说明未确认剧本只能生成 `is_preview=true` 的预览；
2. 人工确认剧本后重新生成正式草案；
3. 查看每个任务的演员清单、道具清单和预计时长；
4. 查看 `parallel_group` 与 `parallel_reason`，解释哪些场次可以并行；
5. 展开“调度 Agent 工具调用链”，依次查看检查确认门槛、提取场次需求、划分并行组、读取配乐/预算/发票/服装资源（有资源时）、查找共同档期和最终校验；
6. 在“演员排练表”点击自动排班，查看最早共同空闲区间；
7. 如果没有共同时间，展示 `unassigned_reason`、`conflict_priority` 和候选替代方案，区分“缺少演员档期”和“演员之间没有共同空闲时间”；
8. 在“演员排练表”打开某个未排班任务的“人工覆盖排班”，提交导演确认的时段，观察任务变为 `overridden` 且新增 `apply_manual_override` 工具调用。
9. 在“批量确认排练室（可选）”中填写 `排练室 A`，自动排班成功后点击“批量确认已排任务”，观察多个任务一次变为 `overridden`，并说明 trace 中的 `validate_room_booking` 与接口返回的 `atomic=true`；如果把两个共享演员、道具或排练室的任务改成重叠时段，或重复提交已经确认的任务，整批会被拒绝。

如果先在“音乐与预算”保存一条配乐时间点、一个预算项目和一张待核验发票，再在“资源管理”保存一条维修中的服装，重新生成调度草案后，排练任务下方会显示资源上下文快照、预计/实际金额、发票总额、已核验金额和服装待处理项；实际金额超出预算、发票未关联/待核验或服装不可直接使用时，页面和 Agent 运行记录都会保留人工确认 warning。这个快照只说明 Agent 生成草案时读到了什么，不会替导演自动改预算、确认付款或把服装维修记录当成可用资源。

面试时可以强调：并行任务只是资源冲突图的可解释分组，自动排班则是在每个任务需要的演员时间区间上做交集，并维护已占用区间，避免同一演员重叠排练；当约束无解时，Agent 输出可审查的替代方案，人工覆盖也不会被伪装成算法成功。

### 4. 对词 Agent

进入“对词训练”，选择第一场和“小林”：

- 先用“原词模式”，不配置 API 也能推进；
- 输入接近原台词的内容，展示相似度反馈；
- 切换“适应性模式”时，LLM 只能修改对方回应，不能改变角色、台词数量或原始剧本；
- 在“角色语气约束”选择“克制”，补充本轮排练上下文；Agent 会把它们写入会话，并在下一轮读取最近 transcript 保持表演意图连续；
- 没有模型或调用失败时，界面显示 `fallback`，仍返回原词并继续排练；
- 刷新页面后确认已保存的会话游标、完整 transcript 和下一句原词仍可恢复，说明后端不会信任客户端直接跳过台词。

### 5. 版本变化与下游影响

在“版本追踪”中选择刚保存的两个版本并比较：

- 查看新增/删除/修改场次、演员、道具和带行号的台词差异；
- 查看“下游影响提醒”，理解为什么已有排班、对词进度或道具结论可能失效；
- 点击卡片中的入口回到“演员排练表”“对词训练”或“资源管理”，由导演人工确认后重新生成结果。

### 6. 舞台可视化、资源与知识沉淀

依次打开以下侧栏入口，快速展示 Agent 的证据边界：

- “舞台可视化”：角色头像位置、道具位置、上场/下场/走位/台词事件，以及无法确认位置的 warning；
- “资源管理”：维护椅子、手电筒等库存，检查单场道具是否就绪；
- “资源变更记录”：修改一次库存或预约，展示新增/修改/删除字段和审计摘要；
- “音乐与预算”：记一条转场音乐时间点，登记一个预算项目和一张待核验发票，展示未关联/待核验提醒；
- “场记档案”：记录一句带行号的现场事实，Agent 只补标签，不改写原话；
- “排练复盘”：填写产出和反馈，查看镜子 Agent 的亮点、阻塞项和下一步动作；
- “排练度量”：切换 7/30/90 天窗口，查看趋势、产出覆盖率、高频阻塞和 Agent 路径，并回指最近记录；
- “Agent运行记录”：回看刚才的解析、调度、排班、对词、资源检查或问答运行，展开步骤 trace、耗时和降级原因；调度草案与自动排班会按根 Run 展示关联运行链；查看最近 30 天失败率、降级率和失败步骤 Top 8；
- “建议收件箱”：提交安全建议，展示明确安全信号触发的高优先级；
- “知识资产”：保存不改写的格言，或生成带 `rules/llm/fallback` 标记的宣传文案。

## 三、面试时的 60 秒项目介绍

> 我做的是面向话剧排练的多 Agent 协作平台。它把剧本解析成带来源行号的结构化场次，再经过导演人工确认；剧本问答 Agent 先检索台词、舞台提示和场次上下文，再基于证据组织回答；调度 Agent 生成演员、道具、时长和并行任务，并从演员时间池中计算最早共同空闲区间；复盘和度量 Agent 保留原始反馈，再生成可回溯的亮点、阻塞、下一步和活动趋势。对词 Agent 以原始台词为事实锚点，支持严格原词和 LLM 适应性回应；舞台 Agent、资源 Agent 和知识资产 Agent 分别负责走位证据、资源就绪和宣传内容。整体设计的重点不是让 LLM 直接改数据，而是用 Pydantic 结构化输出、SourceSpan 证据、人工确认节点、用户隔离存储和规则降级，把不确定的模型能力放在可审计的边界内。

演示最后打开“Agent运行记录”，选择刚才的一条运行记录，说明 Agent 并非黑盒函数：页面可以回看“构建证据 → 检索 → 组织回答”或“生成任务 → 匹配档期 → 解释未排班”等步骤；选择自动排班记录时，还能看到它依赖的调度草案父运行；如果没有模型服务，也能看到清晰的规则路径和降级原因。

## 四、常见追问与回答框架

### 为什么需要 Agent，而不是普通 CRUD？

CRUD 负责保存剧本、档期和记录；Agent 负责把非结构化输入变成带约束的下一步决策。例如调度 Agent 要从场次抽取资源、计算并行关系并给出未排班原因，镜子 Agent 要从原始反馈提炼亮点、阻塞项和行动项。每个 Agent 都有输入、结构化输出、工具/规则、失败分支和可解释 trace。

### 为什么不是强制“先解析剧本，再做所有事情”？

因为数据依赖不同。正式调度依赖人工确认后的场次结构，但演员档期、场记、排练反馈、建议和不关联剧本的宣传文案都可以独立使用。前端把入口独立出来，后端只在真正需要上下文的接口校验 `script_id` 和 `scene_id`。

### 如何防止 LLM 胡编或破坏剧本？

原始文本和 `SourceSpan` 单独保存；人工确认只能改场次元数据，不能改台词原文和来源行号。LLM 输出先经过 JSON 解析和 Pydantic 校验，角色名、台词数量和关联场次再做业务校验。失败时回退到规则结果，并在 `engine`/`note` 中说明实际路径。

### 自动排班的算法是什么？

先按演员建立日期和区间索引，再对一个任务所需的全部演员求共同可用区间，从最早日期和最早边界开始尝试。成功后把该任务区间写入演员 busy 表；后续任务跳过重叠区间。如果某演员没有任何档期，原因是缺少档期；如果所有演员有档期但交集为空，原因是没有共同空闲时间。

### 剧本问答的 RAG 如何防止幻觉？

检索器只从当前用户的当前剧本版本生成带场次和原文行号的证据单元；回答器只能引用这些证据 ID。规则回答没有命中就停止，LLM 回答如果没有引用有效证据或结构校验失败，也会回退到规则结果。这样 LLM 的职责是组织表达，不是创造剧本事实。

### 并行任务如何保证安全？

每场任务转换成 `character:*` 和 `prop:*` 资源集合。没有共同资源的任务可进入同一并行组；有共享演员或道具时分到不同组，并把共享资源写进 `parallel_reason`。正式自动排班仍以演员实际时间冲突校验为最后一道约束。

### 为什么要保留规则分支？

规则分支让项目在没有 API Key、模型限流或网络异常时仍可演示和运行，也让测试结果稳定。LLM 分支负责增强自然语言表达，不负责替代事实来源。这样可以把“模型效果”和“业务可用性”解耦。

### 如何处理多用户数据隔离？

所有剧本、档期、调度、场记、建议、格言和宣传文案路径都通过当前用户 ID 写入 `data/users/{user_id}/...`；API 先通过 Bearer Token 获取用户，再校验关联的剧本和场次属于该用户。没有 Token 的知识资产接口返回 401。

### 目前最值得继续做什么？

当前版本已经有核心 Agent 的用户隔离运行记录、版本变化下游提醒、资源变更审计、可筛选审计时间线、调度工具阶段/结果合同、调度/排班父子 Run、冲突替代方案、批量排班确认及重复提交拒绝、排练室约束、配乐/预算/发票/服装资源快照、对词会话状态、角色语气/上下文记忆，以及两份原创样本上的 LLM mock 合同评估。下一步更值得做的是增加更多剧本样本，并从剧本文本抽取更细的服装需求。
